# MUREEH — UX & USABILITY AUDIT

**Date:** 2026-09-11  
**Source of truth:** current branch at `0deb3ba` before this UX pass

## Scope and method

Repository architecture, routes, contexts, services, role guards, API boundaries, customer ordering, manager/staff surfaces, tests, design tokens, prior design/security audits, and responsive classes were inspected. This is a code/DOM audit; no claim of real-browser visual validation is made.

## Implemented role map

| Role | Primary goal / frequent critical tasks | Dangerous actions | Needed information | Typical device |
|---|---|---|---|---|
| Anonymous customer | Browse, customize, submit and track a QR-bound table order; request service | Cancel a pending order | Restaurant/table context, availability, final prices, cart, understandable order/request status | Personal phone, low familiarity, occasional |
| `RESTAURANT_MANAGER` | Understand current operations; resolve exceptions; manage menu, tables, staff and restaurant | Deletes, structural settings, subscription and tenant management | Urgent calls/orders first, then operational and historical metrics | Desktop/tablet and phone, daily |
| `WAITER` / `STAFF` | Respond to calls; progress relevant orders; update table status | Incorrect status transitions | Active calls, tables, ready orders | Phone/tablet, very frequent |
| `CASHIER` | Create POS orders, collect payment, settle tables, retrieve receipts | Payment/settlement | Unpaid orders, table bill, tender/change | POS desktop/tablet, continuous |
| `KITCHEN` | Move orders through preparation to ready | Premature/incorrect status update | New/preparing orders, age, modifications | Shared KDS display/tablet, continuous |
| `PLATFORM_ADMIN` / `SUPER_ADMIN` | Manage restaurants, onboarding, lifecycle and audit state; may inspect tenant operations | Tenant suspension/activation and cross-tenant administration | Platform overview plus explicit tenant context | Desktop, periodic |

No separate customer account role exists. `STAFF` is an implemented general service role; it is not treated as a new invented role.

## Prioritized findings

| Severity | Role | Screen | Problem / evidence | Smallest safe recommendation |
|---|---|---|---|---|
| **P0** | Customer / low-vision users | Entire customer menu | `CustomerLayout` rewrites viewport to `user-scalable=no` and prevents iOS pinch gestures, reversing the repository's prior WCAG zoom fix. | Remove screen-scoped zoom suppression; retain existing responsive/touch behavior. |
| **P0** | Customer | Waiter request | UI marks a call successful and starts a 60s cooldown immediately although `callWaiter` returns before the API response. Failed calls therefore look successful; duplicate state is not reliably represented in public context. | Await the existing API result, disable during submission, enter submitted state only on success, preserve server limiter. |
| **P0** | Customer | Order tracking | A hardcoded “12–18 minutes” is displayed for every order despite no such value being supplied by the order API. This can mislead guests and staff. | Show live-sync reliability/state, not a fabricated estimate; use actual states only. |
| **P0** | Staff roles | Manager workspace entry | Every role initializes to `OVERVIEW`; an effect later redirects unauthorized roles to the first navigation item. Waiters land on orders although waiter calls are their highest-interruption workflow; users see a transient irrelevant destination. | Resolve initial tab synchronously from the authenticated role and allowed tabs. |
| **P1** | Manager / all staff | Navigation | 13 manager destinations are a flat list and the mobile sheet labels them only as “section 01…”, forcing feature scanning rather than task recognition. | Group existing destinations into Operations, Restaurant, Team, Growth and Settings without adding routes or changing permissions. |
| **P1** | Manager | Dashboard | Existing KPI cards are strong, but urgent new/ready orders and waiter calls compete with analytical revenue at the same level. | Add a compact “needs attention” queue using only supported live data and direct tab routes. Keep analytics intact below. |
| **P1** | Customer | Drawers/modals | Product detail and cart show dynamic totals well; however several customer overlays lack complete dialog semantics and tracking lacks the shared Escape/scroll-lock behavior. | Incrementally add `role=dialog`, labels and shared dialog behavior without changing visual treatment. |
| **P1** | Customer | Header/mobile | Cart count is visible on mobile but total is hidden, reducing the persistent cart mental anchor. | Include the actual current total when non-empty while preserving the same button language. |
| **P1** | Customer | Ready notification | A large interruptive completion modal duplicates persistent tracking and asks dismissal before continuing. | Prefer a non-blocking persistent update into tracking; retain an accessible notification if operationally necessary. |
| **P1** | Waiter | Calls list | `ACKNOWLEDGED` calls are excluded from both active and resolved lists, despite being an actual backend state. | Render pending and acknowledged distinctly and expose acknowledge → resolve progression. |
| **P2** | Manager | Empty/search states | Several states are contextual, but order-filter empty copy conflates “no orders” with “no matches.” | Tailor copy and offer filter/search reset. |
| **P2** | All | Localization | The UI is Arabic-first but has no i18n resource system; Arabic and English phrases are embedded throughout components. | Establish resources before claiming multilingual support; do not introduce a parallel one-off mechanism in this pass. |
| **P2** | All | Form safety | Large branding/product forms do not consistently expose reliable dirty-state leave protection. | Add only after a shared, testable dirty-state pattern exists. |

## Existing strengths intentionally preserved

- Anonymous, QR-bound customer journey and tenant/session protections.
- Server-side pricing and existing product final-price calculation.
- Persistent cart count/total on desktop and active-order floating state.
- Actual order state machine (`PENDING → PREPARING → READY → SERVED`, plus cancellation).
- Role/server authorization and tenant isolation.
- Dark luxury identity, tenant branding, typography, tokens, card/radius/shadow language and RTL-first layout.
- SSE with restrained polling fallback, contextual toasts, and current responsive system.

## Validation plan

Targeted component/source tests will cover accessible zoom, reliable waiter submission, actual order-status copy, role-first navigation and navigation grouping. Then run TypeScript/build, unit tests, lint, and available guard tests. Database-backed E2E requires the documented disposable PostgreSQL environment and will not be represented as run unless it is actually available.
