# تقرير تدقيق: هل تبقى البيانات بعد تعطّل الخادم؟

**التاريخ:** 2026-09-11
**النطاق:** `/server` بالكامل — المسارات (`public`, `manager`, `admin`, `auth`, `uploads`)، الخدمات (`realtime`, `backup`, `audit`, `plans`)، قاعدة البيانات (Prisma/PostgreSQL).

---

## الخلاصة في سطر واحد

> **نعم** — كل البيانات الأساسية (المطاعم، الأطباق، الطاولات، الفواتير، الدفعات، الموظفين، الاشتراكات، سجلّات التدقيق) محفوظة في **PostgreSQL** وتبقى بعد أي تعطّل أو إعادة تشغيل.
> لكن هناك **ثلاث فجوات** يجب الانتباه لها: **الصور المرفوعة** (تُخزَّن على قرص الخادم وليس في قاعدة البيانات)، و**حالة الوقت-الحيوي** (اتصالات SSE وبعض عدّادات منع الإساءة)، و**مسار واحد غير ذرّي** في تسوية الطاولة.

---

## 1) ما الذي يبقى بعد التعطّل؟ (مضمون)

كل ما يمرّ عبر Prisma يُحفَظ في PostgreSQL بمعاملات مُلتزَم بها (committed transactions):

| البيانات | مكان الحفظ | يبقى بعد الكراش؟ |
|---|---|---|
| المطاعم، الفروع، الهوية البصرية (`logoFit`/`logoPosition`، الألوان…) | PostgreSQL | ✅ |
| الباقات والاشتراكات (`Plan`, `Subscription`) | PostgreSQL | ✅ |
| التصنيفات، الأطباق، الأحجام، الإضافات | PostgreSQL | ✅ |
| الطاولات ورموز QR | PostgreSQL | ✅ |
| الفواتير وبنودها (`Order`, `OrderItem` مع لقطات الاسم/السعر) | PostgreSQL | ✅ |
| جلسات الطاولة (`TableSession`) | PostgreSQL | ✅ |
| الدفعات والإيصالات (`Payment`) | PostgreSQL | ✅ |
| نداءات النادل (`WaiterRequest`) | PostgreSQL | ✅ |
| الموظفون وحسابات المنصة | PostgreSQL | ✅ |
| سجلّات التدقيق (`AuditLog`) | PostgreSQL | ✅ |

أمثلة على كتابات **ذرّية** (atomic) مثبتة في الكود:
- `POST /api/public/orders` — إنشاء الطلب + بنوده عبر nested create في معاملة واحدة.
- `POST /api/manager/payments` — تحديث الفواتير المدفوعة + إنشاء الإيصال داخل `prisma.$transaction` مع حماية من السباق (`PAYMENT_RACE`).
- تغيير الباقة، تسوية الدفع، إلخ — كلها عبر `$transaction` أو upsert/update مفرد.

## 2) ما الذي **لا** يبقى؟ (يُفقَد عند الكراش)

| العنصر | السبب | الأثر الفعلي |
|---|---|---|
| **الصور المرفوعة** (شعار/غلاف/صور الأطباق) | تُكتب إلى مجلد `uploads/` على قرص العملية، وليس في قاعدة البيانات | على خادم بقرص دائم تبقى؛ لكن على **Render free tier** (قرص مؤقت) **تُفقد** عند إعادة النشر/إعادة التشغيل، وتصبح روابط `/uploads/…` في قاعدة البيانات مكسورة |
| **اتصالات SSE (الوقت الحيوي)** | `realtime.ts` يحتفظ بالعملاء في `Map` داخل الذاكرة | تُقطع، ثم يعيد العملاء الاتصال تلقائيًا — **لا تُفقد أي بيانات** |
| **عدّادات منع الإساءة** (rate-limit) | مخزن في الذاكرة | تُصفَّر فقط — لا علاقة لها بالبيانات |
| **سلة العميل غير المؤكدة** (cartItems) | حالة React في المتصفح فقط | تُفقد عند تحديث الصفحة — يجب الضغط "إرسال الطلب" لتُحفظ في الخادم |
| **طلبات لم تلتزم بعد** (قيد التنفيذ وقت الكراش) | معاملة PostgreSQL غير الملتزَم بها تُتراجع تلقائيًا (rollback) | لا تُحفظ ولا تُفسد — سلوك سليم |

> قاعدة بيانات PostgreSQL نفسها تسجّل كل كتابة في WAL، وبالتالي أي كتابة أُرسل ردّها للعميل تكون محفوظة حتى لو انقطع التيار بعدها بلحظة.

## 3) مسار غير ذرّي (خطر تناقض جزئي — وليس فقدان بيانات)

`POST /api/manager/tables/:id/settle` (تسوية حساب الطاولة):

1. ✅ الدفعة + الفواتير غير المدفوعة → داخل `$transaction` (ذرّي).
2. ⚠️ ثم 4 عمليات كتابة **متتابعة خارج المعاملة**: تمييز باقي الفواتير كمدفوعة → تصفير الطاولة → إغلاق الجلسة → حلّ نداءات النادل.

إذا انقطع الخادم بين هذه الخطوات، قد تبقى الحالة غير مكتملة (مثلًا: فواتير مدفوعة لكن الطاولة ما تزال "مشغولة"). **لا تفقد بيانات، لكنها قد تظهر غير متسقة** — يُنصح بدمجها في `$transaction` واحد.

## 4) ما تم إصلاحه في هذا التدقيق

1. **`server/routes/uploads.ts`** — بعد كتابة الصورة أصبحنا ننفّذ `fsync` على الملف **وعلى المجلد الأب**، بحيث أن الرد الناجح يعني أن الملف ثابت فعليًا على القرص (وليس في ذاكرة نظام التشغيل فقط).
2. **`server/config.ts`** — إضافة `STORAGE_DRIVER` و`UPLOAD_DIR` إلى التحقق المركزي. عند اختيار `s3`/`supabase`/`cloudinary` (غير منفَّذة بعد) يطبع الخادم **تحذيرًا صريحًا** بدلًا من الصمت والكتابة محليًا.
3. **`server/services/backup.ts`** — أصبح `pg_dump` يقرأ اتصاله من `DATABASE_URL` نفسها (كان سابقًا مكتوبًا بثوابت `localhost/postgres/restaurant_saas` قد ينسخ من قاعدة خاطئة).
4. **`server/index.ts`** — جدولة نسخ احتياطي اختيارية عند الإقلاع (`BACKUP_ENABLED=true`، كل `BACKUP_INTERVAL_HOURS`، افتراضيًا كل 24 ساعة) مع `DB_PASSWORD`.
5. **`.env.example`** — توثيق المتغيرات الجديدة وتحذير القرص المؤقت.

## 5) توصيات (لضمان البقاء الكامل في الإنتاج)

1. **انقل الصور إلى Object Storage** (S3/Supabase/Cloudinary) — `STORAGE_DRIVER` مُعرَّف مسبقًا، نفّذ برنامج التشغيل أو اربط `UPLOAD_DIR` بـ **قرص دائم (persistent disk)**.
2. **فعّل النسخ الاحتياطي** `BACKUP_ENABLED=true` + انسخ ملفات `backups/` خارج الخادم (القرص نفسه قد يفشل).
3. **دمج خطوات تسوية الطاولة** في `$transaction` واحد لإغلاق فجوة التناقض الجزئي.
4. **فعّل PITR/أرشفة WAL** على Postgres المُدار لاستعادة لنقطة زمنية.

---

### الخلاصة النهائية
> البنية **سليمة**: قاعدة البيانات هي مصدر الحقيقة الوحيد، وكل المعاملات النقدية والحرجة ذرّية. النقطة الوحيدة التي يمكن أن تخسر منها **ملفات فعلية** (وليس سجلات) هي **الصور المرفوعة على قرص مؤقت** — وهذا يعتمد على بيئة النشر، وتمت معالجته جزئيًا بالـ fsync وبتوثيق/تحذير واضح وتفعيل النسخ الاحتياطي.
